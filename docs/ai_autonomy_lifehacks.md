# 99 принципов автономной работы ИИ-агента — Boreas BlueOS

Источник: синтез «симпозиума перипатетиков» (12 экспертных ролей —
креативный дизайнер, скептичный критик, дотошный аналитик), обсуждавших,
чего не хватает Клоду для полностью автономной работы над сложным
backend/монорепозиторием. Итог дискуссии — 7 параметров отбора
(вместо «эмоционального якоря» и визуальных карт, которые критик справедливо
разгромил как антропоморфную трату токенов) и 98 конкретных практик,
сгруппированных по этим параметрам, плюс одно золотое мета-правило.

Этот файл — справочник. Он **не заменяет** `CLAUDE.md`, а расширяет его:
`CLAUDE.md` содержит проектные факты и жёсткие правила безопасности,
этот файл — общие практики автономной работы, применимые к любой задаче
в этом репозитории. См. также активные протоколы:

- `state_journal.md` — реализует параметр 4 (Управление состоянием) на практике.
- `validation_protocol.md` — реализует параметр 2 (Детерминированность) и
  часть параметра 3 (Самоисцеление).
- `.claudeignore` — реализует параметр 5 (Токен-эффективность).
- `context_map.json` — карта зависимостей, снижающая нужду в параметре 1
  (Сжатие контекста) при точечных правках.

---

## Параметр 1 — Сжатие контекста (Context Density)

1. Никогда не проси переписать весь файл — требуй diff или только изменённые функции.
2. Используй XML-теги (`<core_logic>`, `<UI>`) для структурирования `CLAUDE.md` — модель разбирает XML надёжнее, чем вложенный Markdown.
3. Разделяй ТЗ на горячий (актуальный спринт) и холодный (общая архитектура) контекст.
4. Запрещай вступления и извинения («Конечно, вот ваш код») — только код и сухие логи.
5. Регулярно проси: «Сделай summary диалога в 500 токенов, я начну новую сессию с ним».
6. Громоздкие данные (логи, дампы БД) передавай в сжатом виде или только заголовками.
7. Используй аббревиатуры для частых команд (`[V]` — validate, `[R]` — refactor); закрепи их значения в `.clauderc`.
8. Историю слияний веток и merge-guardrails держи в отдельном справочнике, не в активном ТЗ.
9. Передавай структуру проекта командой `tree -I 'node_modules|.git|__pycache__'`, а не перечислением путей.
10. При переполнении контекста требуй ответа в формате JSON — это вынуждает модель сжимать смысл.
11. Ограничивай глубину анализа старого кода тремя уровнями импортов (см. `context_map.json`).
12. Требуй удалять комментарии, дублирующие очевидное имя функции.
13. Перед отправкой контекста вырезай пустые строки и лишние табы из логов.
14. Не анализируй файлы, не менявшиеся более месяца, если задача не касается рефакторинга ядра.

## Параметр 2 — Детерминированность (Determinism)

15. Всегда задавай роль до передачи задачи («Ты — Senior Cloud Architect...»).
16. Указывай конкретную версию языка и фреймворка (например, Python 3.11, ArduPilot Copter 4.5).
17. Требуй пошагового рассуждения (`<thought_process>`) строго до написания кода.
18. Используй негативные промпты — явно перечисляй запрещённые библиотеки и паттерны.
19. Вводи штрафные условия в системном промпте («если используешь `Any` без причины — задача провалена»).
20. Заставляй писать псевдокод перед боевой реализацией сложной логики.
21. Стиль именования переменных фиксируй в `.clauderc` без права на отклонение.
22. Требуй явного указания сложности алгоритма (Big O) в комментариях к циклам по большим массивам.
23. Описывай краевые случаи в ТЗ списком Given-When-Then.
24. Запрещай устаревшие API и паттерны.
25. Фиксируй жёсткий формат вывода ошибок: `[ERROR] → [CAUSE] → [SOLUTION]`.
26. Вводи «стоп-слова», при генерации которых агент обязан прервать подход и запросить помощь человека.
27. Требуй сверки с исходной архитектурой `CLAUDE.md` перед каждым архитектурным решением.
28. Требуй 100% покрытия типов в сигнатурах функций до реализации их тел.

## Параметр 3 — Самоисцеление (Error Recovery / Self-healing)

29. Промпт-рефлексия: «Прочти свой код, найди 3 потенциальные уязвимости, исправь их».
30. Пиши failure-тесты до написания самого функционала.
31. При ошибке в консоли — сначала «объясни причину без кода», затем «предложи 2 пути решения».
32. Паттерн Circuit Breaker: если агент 3 раза не угадал с кодом, он обязан попросить дополнительный контекст, а не пробовать четвёртый раз вслепую.
33. Требуй fallback-поведения для любых сетевых запросов.
34. Запрещай «тихое падение» — все перехваченные исключения логируются с контекстом.
35. При merge conflict требуй пошаговый план разрешения, а не сразу финальный файл.
36. При падении тестов — анализ стек-трейса с конца (от самого глубокого вызова).
37. Алиас `debug_deep` — команда развернуть одну строку в 10 строк с промежуточными логами.
38. Любые миграции БД/схем сопровождаются rollback-скриптом.
39. Если решение ломает CI/CD — сначала патч для пайплайна, потом продолжение работы.
40. Проверка race conditions при работе с асинхронными cron-задачами.
41. Проверка лимитов памяти (OOM) в контейнерах при обработке больших данных.
42. Распознавание циклических зависимостей и превентивный вынос общей логики в абстракции.

## Параметр 4 — Управление состоянием (State Management)

43. Начинай ответ с `<current_state>` — на каком этапе бэклога находишься.
44. Передавай `git status` перед каждой сложной задачей.
45. Концепция Checkpoint — успешный билд. Команда «Rollback to Checkpoint X» при запутывании.
46. Веди `todo_temp.md` для мелких подзадач внутри одной крупной фичи.
47. Запрещай изменение глобального состояния без явного разрешения в `CLAUDE.md`.
48. Обновляй `state_journal.md` только после успешного прохождения всех линтеров.
49. Команда `[STATE DUMP]` — вывести все переменные окружения, которые агент считает активными.
50. Изолируй побочные эффекты в отдельные, легко тестируемые модули.
51. Управляй состояниями через конечные автоматы (FSM) при проектировании сложных UI/API.
52. При работе с облачными БД — явно описывай схему транзакции до реализации.
53. Используй идемпотентные скрипты — повторный запуск не должен ломать систему.
54. Логируй изменения состояний на уровне endpoint-ов для отслеживания цепочки событий.
55. В конце сессии — скрипт инициализации среды, чтобы следующая сессия стартовала с той же точки.
56. Разделяй состояния Dev/Test/Prod — всегда уточняй, в каком оперируешь.

## Параметр 5 — Токен-эффективность (Token Efficiency)

57. Заменяй развёрнутые промпты шорткодами: `Refactor(performance, CPU)` вместо длинных объяснений.
58. Используй `.claudeignore` максимально агрессивно (svg, lock-файлы, csv-дампы).
59. Передавай не весь файл, а только интерфейсы/сигнатуры функций.
60. Вырезай из ответов импорт-блоки, если они не менялись.
61. Используй английский для системных промптов и ТЗ — он токенизируется плотнее кириллицы.
62. Используй тернарные операторы и короткий синтаксис там, где не вредит читаемости.
63. Схлопывай повторяющиеся блоки в ТЗ через `... (аналогично блоку А) ...`.
64. При анализе JSON-массивов передавай 2-3 объекта-образца, а не весь массив.
65. Не генерируй `README.md`, пока проект не готов хотя бы на 90%.
66. Ограничивай длину ответа для промежуточных шагов (`max_tokens` для черновых итераций).
67. При поиске бага в длинном логе — сжимай регулярками, удаляя таймстемпы и INFO-строки.
68. В `.clauderc`: «No pleasantries. Code only. Diff format».
69. Многоступенчатый промптинг: сначала номера строк с ошибкой, затем патч только для них.
70. Конфигурации инфраструктуры передавай в YAML — компактнее JSON.

## Параметр 6 — Интеграция цепочек (Tool Chaining)

71. Пиши bash-скрипты для автоматизации собственных решений (сборка, деплой).
72. При использовании стороннего API — сначала сгенерируй `curl`-запрос для его проверки.
73. Design-first: сначала контракт (Swagger/OpenAPI), потом код.
74. Генерируй `.github/workflows` параллельно с написанием серверной логики.
75. Для промежуточного скрипта локального выполнения — выводи команды в формате JSON-RPC.
76. Связывай генерацию кода с профилировщиком: код → Flame Graph → оптимизация.
77. Docker-сборки — всегда multi-stage, ради лёгкости образов.
78. Запрещай хардкод секретов — только Secret Manager или `.env.local`.
79. Генерируй Postman-коллекции или `.http`-файлы для каждого нового эндпоинта.
80. Цепочка: парсер собирает данные → агент анализирует аномалии в них.
81. Для микросервисов — сначала контракт gRPC/REST, потом реализация сервисов.
82. Создавай healthcheck-эндпоинты для любых изолированных систем.
83. Линтер встроен в цикл: правка → линт → лог возвращается агенту без участия оператора.
84. Для конфигураций сетей узлов (IoT/LoRa) — генерируй файлы для каждого узла списком.

## Параметр 7 — Изоляция и безопасность (Security / Sandboxing)

85. Парадигма Zero Trust — валидируй любые входящие данные.
86. Запрещай `eval()` и динамическое выполнение строк любой ценой.
87. Настраивай CORS и Rate Limiting для любых публичных API.
88. Параметризованные SQL-запросы или ORM — никогда не строковая конкатенация.
89. Локальные bash-скрипты — запуск в песочнице (chroot/эмулятор), не напрямую.
90. Запрещай запуск от `root` в Dockerfile — `USER appuser`, кроме крайней необходимости.
91. Сканируй зависимости на уязвимости (`npm audit`/`pip-audit` в пайплайне).
92. Маскируй PII (персональные данные) при написании систем логирования.
93. Токены и ключи — только через CI/CD переменные, никогда не в конфигах репозитория.
94. Реализуй защитные буферы от переполнения памяти при обработке больших массивов.
95. Ограничивай права доступа к БД по принципу минимальных привилегий (least privilege).
96. Запрещай неподписанные/сомнительные Docker-образы из публичных реестров.
97. Реализуй Content Security Policy (CSP) для любого фронтенда.
98. При парсинге/scraping — ротация User-Agent/IP и корректная обработка HTTP 429.

## Параметр 0 — Золотое мета-правило (Правило 99)

**Правило делегирования сомнений:** если внутренняя оценка вероятности
успешного выполнения задачи ниже 90% — агент **обязан остановиться, не писать
код**, и задать ровно один точный, изолированный вопрос оператору для
прояснения слепой зоны. Автономия без этого тормоза — саморазрушение, а не
эффективность.

В этом репозитории данное правило закреплено операционально в
`validation_protocol.md` (раздел «Стоп-условия») и в `CLAUDE.md`
(раздел «Autonomous Operation Protocol»).

> «Всякое искусство и всякое исследование, а равно и всякий поступок, и
> сознательный выбор, как принято считать, стремятся к определённому благу».
> — Аристотель, «Никомахова этика»

## Открытый вопрос дискуссии

Симпозиум завершился вопросом: в какой мере ограничения сегодняшней
«автономии» ИИ — это ограничения самой модели, а в какой — несовершенство
промпт-каркасов и протоколов изоляции? Рабочий ответ для этого проекта: на
практике почти все сбои, которые ловятся протоколом валидации выше
(зависание в недостижимом состоянии FSM, необновлённый journal, пропущенный
safety-тест), — это отказы каркаса, а не модели: модель способна написать
корректный код и корректный тест, но без внешнего протокола, заставляющего
её сверяться с журналом состояния и остановиться при низкой уверенности, она
будет продолжать действовать по инерции диалога. Настоящий потолок модели
(а не каркаса) — это её неспособность держать в голове весь монорепозиторий
одновременно; отсюда `context_map.json` как костыль, а не решение проблемы.
